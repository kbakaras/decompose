# дерево·дел / decompose

дерево·дел (английское название проекта — decompose) — keyboard-first collaborative tool для иерархической декомпозиции работы, задач и рассуждений. В русскоязычном интерфейсе используй название «дерево·дел»; технические идентификаторы decompose сохраняются.

## Источники истины

Перед любыми существенными изменениями прочитай:

- `docs/product.adoc` — назначение продукта, философия и функциональные требования.
- `docs/architecture.adoc` — архитектурные принципы и выбранные технологии.
- `docs/open-questions.adoc` — вопросы, которые ещё не решены и не должны молча превращаться в архитектурные факты.

Эти документы являются источником истины по проекту. Если в ходе работы принимается существенное решение, обновляй соответствующий документ.

## Принципы разработки

- Предпочитай самое простое решение, достаточное для небольшой команды разработчиков или одной компании.
- Не проектируй систему под гипотетический Internet-scale SaaS.
- Семантика доменной модели важнее графического представления.
- Structure is data; layout is view.
- Координаты узлов не являются частью предметной модели, если только позже не будет принято отдельное решение.
- Основные пользовательские сценарии должны быть keyboard-first.
- Не превращай Decompose в универсальный diagramming tool, mindmap editor, issue tracker или project management system.
- Не добавляй функции «на будущее» без явной потребности.
- Не вводи лишние сервисы, runtime или инфраструктуру, если задачу можно решить внутри одного приложения.
- Collaboration, layout и rendering по возможности реализуй готовыми зрелыми библиотеками. Собственный код концентрируй на предметной модели и UX Decompose.

## Стиль работы

- Сначала проверяй существующие решения и ограничения выбранных библиотек, затем проектируй свой слой поверх них.
- При неоднозначности не придумывай скрытое требование. Зафиксируй вопрос в `docs/open-questions.adoc`.
- Для изменений предметной модели сначала опиши инварианты и операции, затем меняй код.
- Для конкурентных операций над деревом обязательно продумывай convergence и валидность структуры после merge.
- Покрывай доменные операции unit/property-based тестами, а collaboration — тестами с несколькими клиентами.
- При изменении интерфейса следи за аккуратностью вёрстки и соблюдай базовые визуальные принципы: общую сетку, выравнивание элементов, единообразные размеры и отступы, устойчивость на узких экранах и отсутствие скачков в промежуточных состояниях. Проверяй результат в браузере, а значимые геометрические требования закрепляй E2E-тестами.

## Формат документации

Всю внутреннюю документацию проекта, включая README, документы в `docs/`, описание структуры и проектные заметки, веди в AsciiDoc — файлах с расширением `.adoc`. Не создавай Markdown-дубли; при переименовании документов обновляй ссылки на них.

Исключение — `AGENTS.md`: сохраняй это имя и Markdown-формат для совместимости с инструментами агентов. Сторонние зависимости и автоматически созданные отчёты не конвертируй.

## Публичный репозиторий

Исходный код и публикуемый Docker-образ считаются общедоступными. При внесении изменений соблюдай следующие правила:

- Не добавляй секреты, токены, пароли, приватные ключи, `.env`, `session.id`, базы данных, пользовательские схемы, логи с чувствительными данными и сведения, относящиеся к конкретной компании. В примерах и тестах используй вымышленные имена и зарезервированные домены вроде `example.com` и `.test`.
- Проверяй новые и изменённые файлы, build context Docker, содержимое образа, generated artifacts, source maps, OCI labels, `.gitignore` и `.dockerignore`. Нельзя считать собранный код или файлы внутри контейнера приватными.
- Учитывай Git-историю. Удаление данных из текущего дерева не удаляет их из прежних коммитов. При случайной публикации секрета остановись, сообщи о необходимости отозвать секрет и отдельно согласовать очистку истории. Существующие email автора и старые hostname в истории сохранены осознанно. Это не разрешает добавлять новые внутренние адреса и идентификаторы.
- Добавляй только те изображения, тексты, шрифты и другие материалы, которые разрешено распространять публично. Фиксируй происхождение и лицензию сторонних материалов, если они неочевидны.
- Сохраняй актуальными `LICENSE`, `NOTICE` и `THIRD_PARTY_NOTICES`. После изменения зависимостей запускай `npm run licenses`, затем `npm run licenses:check`. Не добавляй зависимость с отсутствующей или несовместимой лицензией без отдельной проверки.
- Сохраняй согласованными лицензию и описание в `package.json`, README, предупреждения о модели безопасности и OCI metadata Docker-образа. Юридические файлы должны попадать в распространяемые frontend и Docker artifacts.
- Не описывай приложение как безопасное для публикации в Internet без дополнительной защиты. Пока в нём нет аутентификации и авторизации, документация должна явно рекомендовать доверенную сеть или внешний access-control слой.
- Перед публичной публикацией запускай `npm test`, `npm run build`, `npm audit` со свежими данными registry и `git diff --check`, а также повторяй поиск секретов, внутренних hostname и специфичных для компании названий в текущем дереве. Историю проверяй, если изменение затрагивает ранее закоммиченные чувствительные данные.

## Проверки

- Сначала запускай относящиеся к изменению unit- и E2E-тесты, затем общие проверки, соразмерные риску изменения.
- Не запускай второй процесс Playwright, пока не завершился первый. Если тестовый порт `4183` занят, найди конкретный процесс и дождись его завершения или адресно заверши его. Не запускай конкурирующий прогон и не останавливай процессы по широкому шаблону.
- Долгий полный E2E-прогон запускай один раз перед сдачей, если масштаб изменения его требует. Сохраняй идентификатор работающего процесса и получай вывод из него до окончательного кода завершения.
- Единичный сбой полного прогона повторно проверяй только после завершения исходного процесса. Отдельно указывай, прошёл ли весь набор одним запуском или только повторно проверенные сценарии.
