= Decompose: архитектура
:figure-caption: Рисунок

== 1. Архитектурные цели

Архитектура должна соответствовать реальному масштабу проекта:

* небольшая команда разработчиков;
* максимум одна компания;
* self-hosted использование;
* один экземпляр приложения в обычном сценарии;
* отсутствие требований Internet-scale SaaS.

Основной принцип:

[quote]
____
Использовать готовые компоненты для rendering, layout и collaboration; собственный код сосредоточить на предметной модели и UX Decompose.
____

== 2. Текущий выбранный стек

=== Frontend

* TypeScript
* React
* React Flow — canvas, nodes, edges, viewport, selection и drag для sibling reorder; свободное размещение выключено
* ELK.js — автоматический hierarchical layout
* Yjs — CRDT и collaborative data model
* y-indexeddb — локальное хранение Yjs-документа в браузере

=== Backend

* Node.js 24 LTS
* TypeScript
* Hocuspocus — WebSocket collaboration server для Yjs, встроенный в основной backend
* SQLite — бинарное состояние Yjs через `@hocuspocus/extension-sqlite`

=== Тесты

Используются:

* Vitest — unit tests
* fast-check — property-based tests для операций над деревом и инвариантов
* Playwright — UI и multi-client collaboration tests

Цель: один application service и один persistent volume.

Реализация использует HTTP-сервер Hocuspocus и Express для static frontend, `/healthz` и `/api/diagrams` на том же порту. WebSocket доступен только на `/collaboration`; принимаются только существующие документы с идентификатором `main` или UUID. Используется штатный lifecycle Hocuspocus для закрытия соединений и сохранения перед остановкой.

`GET /api/diagrams` возвращает список обычных схем, исключая деревья задач трекера; `POST /api/diagrams` создаёт схему с начальным названием, `GET /api/diagrams/:id` проверяет существование и возвращает название. Документы хранятся отдельными строками штатной таблицы `documents` SQLite. Список обычных схем читает текст корня из загруженного документа Hocuspocus либо декодирует сохранённое состояние Yjs. Создание атомарно сохраняет инициализированный документ до HTTP-ответа. Неизвестные документы не создаются при WebSocket-подключении.

Первый root создаётся сервером; клиенты не инициализируют конкурирующие документы. IndexedDB загружается до подключения provider. Production service worker кеширует оболочку приложения для offline reload на localhost и по HTTPS; в dev-сборке он выключен. На HTTP под другим hostname загруженный документ допускает редактирование при потере соединения, но offline reload оболочки не поддерживается.

Одна сборка и один backend допускают одновременную публикацию в корне сайта и под префиксом другого hostname. Vite использует `base: './'`, без конфигурации префикса при сборке или запуске. Reverse proxy снимает внешний префикс перед передачей HTTP-запроса и WebSocket upgrade; backend обслуживает прежние внутренние маршруты. Доверие к `X-Forwarded-*`, доменный allowlist и CORS-разрешения не требуются. Loopback-адреса dev-прокси, healthcheck и прослушивания сервера не являются адресами браузерных запросов.

Перед выдачей HTML сервер устанавливает относительный `<base>` по глубине внутреннего маршрута: `./` для главной страницы и `index.html`, `../` для `tracker/{key}`, `../../` при завершающем слеше. Он не подставляет в HTML hostname или внешний префикс. Обработка SPA-страниц предшествует static middleware; Vite dev использует тот же расчёт при преобразовании HTML. В браузере `appBaseUrl` фиксирует разрешённый `document.baseURI` до первого SPA-перехода; `<base>` также фиксируется полным вычисленным URL. Относительные ассеты, favicon, API, логотип и ссылки сохраняют внешний префикс при прямом открытии и навигации. WebSocket получается из `new URL('collaboration', appBaseUrl)` заменой протокола HTTP/HTTPS на `ws`/`wss`. Разбор маршрута проверяет origin и границу корня приложения; префикс не угадывается по названию сегмента `tracker`.

Service worker регистрируется относительно `appBaseUrl` со scope конкретной публикации. Список ресурсов разрешается относительно scope во время выполнения, имена кешей содержат scope и версию сборки. Очистка затрагивает только прежние версии этого scope; при обновлении корневой установки также удаляется прежний формат её кеша. API не кешируется. Offline fallback получает оболочку из корня кеша и меняет относительный `<base>` под глубину запрошенного маршрута, чтобы вложенная ссылка не искала ассеты внутри `tracker`. Ключи IndexedDB и профиля не меняются; изоляция нескольких независимых backend на одном origin не предусмотрена.

UUID профиля, узлов, placements, маркеров операций и схем создаёт общий `createUuid`. При наличии `globalThis.crypto.randomUUID` используется он; иначе 16 байт из `getRandomValues` преобразуются в UUID v4 с установленными version и variant и записью в нижнем регистре. Это допускает обычный HTTP без secure context. Если нет обоих методов, генератор выбрасывает ошибку; небезопасного fallback нет. Браузер без Web Crypto не поддерживается. Формат прежних идентификаторов, ключи браузерных хранилищ и схема SQLite не меняются; профиль и кеш остаются привязаны к origin.

На пути `/` параметр URL `diagram` выбирает документ; отсутствие параметра означает `main`. Путь `/tracker/{key}` разрешается в UUID задачи. Имя IndexedDB — `decompose:<id>:v1`, поэтому кеш `main` совместим с прежней версией. Последний список обычных схем хранится в localStorage только для offline-навигации; это не источник данных схем. API не кешируется service worker.

Переключением управляет оболочка React: она сохраняет draft, дожидается IndexedDB, загружает целевой документ и явно закрывает прежний provider, presence, undo manager и IndexedDB-соединение. Верхняя панель и логотип остаются смонтированными. Адрес меняется через History API; `popstate` использует тот же lifecycle. Загрузка отменяется при более позднем запросе, переходы сериализованы. При ошибке открытия прежняя схема остаётся доступной. При смене схемы состояние её редактора, layout и undo/redo создаётся заново.

При `pagehide` ещё не подтверждённые IndexedDB изменения Yjs временно сохраняются в sessionStorage вкладки под ключом с идентификатором схемы. После reload они применяются к тому же документу, записываются в IndexedDB, и временный журнал удаляется. Это защита от прерывания транзакции немедленной перезагрузкой, а не замена IndexedDB или резервная копия; она зависит от доступности и квоты браузерного хранилища.

=== Деревья задач трекера

Ключи задач нормализуются в верхний регистр и проверяются общим клиентским и серверным кодом. Сервер выдаёт оболочку по `/tracker/:key`; клиент сначала вызывает `GET /api/tracker/:key`. Только ответ `404` запускает знакомство и затем идемпотентный `POST /api/tracker/:key`. Ошибка сети не считается отсутствием задачи. Существующий документ открывается без имени; отмена знакомства не создаёт документ. Запрос имени не является серверным контролем доступа.

Таблица `tracker_diagrams` в той же SQLite содержит уникальные `tracker_key` и `document_id`, производные `title` и `search_text`, а также `updated_at` в миллисекундах серверного времени. Она создаётся автоматически при конфигурации хранилища; прежние документы и схема Yjs версии 2 не меняются. Транзакция `IMMEDIATE` проверяет привязку и атомарно создаёт документ с ключом в корне и строку каталога. Повторный запрос возвращает прежний UUID, не инициализируя корень заново.

`TrackerStorage` расширяет штатное SQLite-хранилище: при сохранении Yjs сравнивает бинарное состояние с предыдущим и в одной транзакции сохраняет документ, поисковое название и время изменения. Неизменённая повторная запись не меняет время. Название нормализуется из корня; поисковая строка включает ключ и название в нижнем регистре Unicode. Она является производным индексом, не отдельным редактируемым описанием. Presence не хранится в документе и не обновляет каталог. Offline-изменения получают время сохранения после синхронизации.

`GET /api/tracker?q=...&offset=...` выполняет поиск подстроки через `instr`, без SQL-шаблонов. Запрос ограничен 500 символами, `offset` — неотрицательное безопасное целое. Ответ содержит `items` и `nextOffset`, выдача идёт по 20 строк: `updated_at DESC, tracker_key ASC`. Пустой запрос показывает последние изменённые деревья. Строка результата содержит `id`, `trackerKey`, `title`, `updatedAt`; при пустом корне `title` подставляет ключ. `GET /api/diagrams/:id` также возвращает метаданные задачи, если UUID ей принадлежит. Поиск читает индекс, не декодируя весь каталог Yjs; обновление индекса следует обычному debounce сохранения Hocuspocus.

Клиент хранит отдельный объединяемый кеш привязок и результатов под ключом localStorage `decompose:tracker:v1`. Открытые документы сохраняются в прежнем IndexedDB по UUID. При offline-открытии используется сохранённая привязка, а неизвестный ключ требует сервера. Поиск offline ограничен накопленным каталогом и помечается как неполный. В интерфейсе поиск задержан на 250 мс; устаревшие запросы отменяются, переходы используют общий lifecycle сессий и History API.

=== Импорт GraphML

Клиент разбирает XML встроенным `DOMParser`, учитывая пространства имён GraphML и yWorks и объявления ключей `nodegraphics`. DTD и объявления сущностей запрещены; XML не вставляется в HTML, внешние ресурсы не загружаются. Из каждого `ShapeNode` или `GenericNode` извлекаются `NodeLabel`, `Fill` и `Geometry`; геометрия нужна только для детерминированной сортировки детей. Отсутствующие или неконечные координаты и неположительные размеры отклоняются. Остальное оформление и метаданные не переносятся.

`POST /api/diagrams/import` принимает JSON `{nodes: [{id, text, status, children}]}`, где `children` — упорядоченные исходные ID детей. Общая проверка клиента и сервера требует единственное дерево: уникальные непустые ID, допустимые статусы, существующие ссылки, отсутствие повторных родителей и циклов, достижимость всех узлов из единственного корня. Сервер повторяет проверку независимо от клиента. Лимит этого маршрута — 1 МиБ; остальные API-запросы сохраняют лимит 16 КиБ. Число узлов ограничено 1000, клиентский файл — 5 МиБ.

В отдельном `Y.Doc` корень получает ID `root`, остальные узлы и placements — свежие UUID. За одну транзакцию создаются записи узлов и массивы порядка для всех узлов, включая листья; исходные ID и координаты не сохраняются. Полное состояние записывается одним `INSERT` в SQLite, после чего возвращается `201` с `{id, title}`. Ошибка проверки не создаёт документа. Это инициализация, не история пользовательских команд; схема хранения остаётся версии 2. Повтор запроса создаёт другую самостоятельную схему, поэтому клиент блокирует повторное нажатие на время импорта.

== 4. Почему Node.js

Node.js выбран не как универсально «лучший backend», а как самый прямой путь к зрелому Yjs/Hocuspocus стеку.

Преимущества для MVP:

* Hocuspocus работает в родной экосистеме;
* frontend и backend используют TypeScript;
* можно разделять общие типы;
* меньше собственной реализации collaboration protocol;
* ниже риск ошибок в CRDT sync.

Go + ygo остаётся потенциальной альтернативой на будущее, если появится реальная польза от single binary и более лёгкого runtime. Для MVP переход на Go не планируется.

== 5. Почему SQLite

SQLite выбран как основное хранилище, потому что ожидаемый масштаб невелик:

* один backend instance;
* небольшое число пользователей;
* умеренное число документов;
* отсутствие тяжёлой серверной аналитики;
* отсутствие сложного multi-tenant SaaS.

PostgreSQL не требуется на старте.

Переход к PostgreSQL следует рассматривать только при появлении конкретной причины, а не заранее.

== 6. Разделение состояния

Состояние нужно разделять как минимум на три категории.

=== 6.1. Domain state

Хранится и синхронизируется через Yjs.

Примеры:

* node id;
* text;
* status;
* parent;
* sibling order;

Типы узлов (`kind`) и другие семантические свойства в MVP не входят.

Текст клеточки хранится как атомарная строка, а не как `Y.Text`. Во время ввода используется локальный draft; в Yjs записывается результат целиком, включая переводы строк LF. CRLF и CR нормализуются в LF при записи; вставка и GraphML-импорт сохраняют переносы. Название из корня для HTTP API, списка и верхней панели преобразуется в одну строку отдельно, без изменения текста корневой карточки.

=== 6.2. Presence

Эфемерное состояние collaboration.

Примеры:

* пользователь online;
* выбранный узел;
* редактируемый узел;
* cursor/presence metadata.

Используется Yjs Awareness. Постоянный ID браузера хранится в localStorage под ключом `decompose:participant:v1`, выбранное имя — под ключом `decompose:participant-name:v1`; цвет выводится из ID, а не из `doc.clientID`. Существующий ID сохраняется при выборе имени. Если имя отсутствует, профиль считается гостевым: автоматически сформированное имя не заменяет знакомства. Без доступа к localStorage профиль сохраняется только до reload, о чём приложение предупреждает. Это не аутентификация и не учётная запись.

Клиентский профиль наблюдаемый: сохранение имени обновляет интерфейс и поле `user` Awareness без пересоздания provider, Yjs-документа и undo manager. Событие `storage` обновляет другие вкладки. Отсутствующее имя передаётся как `null`; гостевые состояния нужны для подсчёта уникальных ID, но их `activeNode` и `editingNode` не публикуются и не отображаются. Свой профиль учитывается и offline; удалённые участники показываются только при соединении.

Перед изменением данных клиент запрашивает имя через модальную форму. До подтверждения операция не выполняется; она привязана к исходной сессии и отменяется при навигации. После подтверждения повторно проверяется существование целевого узла, а для drag — снимок sibling order. Этот UI-барьер не является серверным контролем доступа; API и хранилище схем не содержат реестра пользователей.

Awareness по-прежнему адресуется уникальными Yjs client ID: нельзя подменять их постоянным пользовательским ID. Индикаторы группируются по идентичности браузера, а выделения и soft lock именованных участников учитываются по соединениям. Пустые служебные awareness-состояния не показываются как участники. При переключении вызывается `provider.destroy()` и удаляется подписка на профиль; при `pagehide` снимается presence и закрывается сокет, при возврате из back-forward cache соединение восстанавливается с актуальным именем.

Серверный hook `onAwarenessUpdate` привязывает повторно появившиеся Yjs client ID к восстановленному соединению. Yjs сообщает их как `updated`, тогда как Hocuspocus 4 автоматически привязывает только `added`. Это позволяет штатному закрытию соединения немедленно снять presence и после reconnect, не дожидаясь тайм-аута Awareness.

=== 6.3. Local UI state

Не синхронизируется как доменная модель.

Примеры:

* viewport;
* zoom;
* локальное выделение;
* открытое меню;
* промежуточная геометрия layout.

Используется React state.

=== 6.4. Сохранённые настройки представления

`settings: Y.Map` хранится в том же документе Yjs, SQLite и IndexedDB. Необязательное поле `textAlign` принимает `left` или `center` и применяется ко всем карточкам схемы, включая редакторы. Отсутствующее или неизвестное значение означает `left` без записи значения по умолчанию. Настройка синхронизируется, работает offline и не меняет структуру дерева. Конкурентные изменения разрешаются атомарно средствами Yjs. Каждая схема имеет независимую настройку; миграция схемы 2 не нужна. После обновления приложения перезагрузи прежние вкладки: старый редактор при сохранении удаляет переводы строк.

== 7. Structure is data; coordinates are view

Предварительное решение:

Не хранить вычисленные `x/y` как источник истины.

В предметной модели хранить:

* parent relationship;
* sibling order;
* возможно, explicit layout hints, если они реально понадобятся.

ELK.js вычисляет координаты на клиенте.

Это означает, что два клиента могут иметь немного различную пиксельную геометрию при сохранении одной и той же смысловой структуры.

== 8. Layout

Основной алгоритм:

* ELK layered;
* направление слева направо;
* layout должен уважать model order;
* по возможности учитывать mental map пользователя при перестроении.

Включены `considerModelOrder.strategy=NODES_AND_EDGES` и `crossingMinimization.forceNodeModelOrder=true`. Входные nodes/edges строятся в порядке обхода проекции. ResizeObserver измеряет высоту клеточек; размеры и координаты остаются локальными. React Flow получает измеренные размеры при каждом обновлении controlled nodes.

Размещение узлов использует `nodePlacement.strategy=BRANDES_KOEPF` и `nodePlacement.bk.fixedAlignment=BALANCED`. Режим балансирует четыре варианта выравнивания вместо выбора одного из них ради компактности, уменьшая риск скачка родителей от верхних детей к нижним при перестановке соседей. Это не требование точного центрирования каждого родителя и не гарантия неподвижности остальных ветвей: размеры поддеревьев и ограничения порядка по-прежнему влияют на раскладку. Координаты вычисляются заново без привязки к предыдущему расположению и без сохранения в документе. Регрессионные тесты проверяют центрирование простого симметричного дерева и ограниченное смещение предков при перестановке в обезличенном примере с неодинаковыми ветвями.

Новая клеточка монтируется прозрачно для измерения и приёма ввода, но показывается вместе со связью только после layout с измеренными размерами. Промежуточная позиция `(0, 0)` не видна. Drag использует штатные callbacks React Flow и локальную preview-позицию; во время жеста ELK не перестраивает схему. После drop preview сохраняется до готовности нового layout, без возврата на старое место между кадрами.

При первом открытии и reload вся диаграмма скрыта до измерения узлов, готовности ELK и установки начального viewport без анимации. Bounds вычисляются из результата layout; `getViewportForBounds` и `setViewport` React Flow вписывают схему до её показа. Отложенный по таймеру `fitView` не используется. Автопрокрутка к active node включается только при последующем изменении цели, чтобы не конкурировать с начальным вписыванием.

Перестановка разрешена только для активной клеточки: её `draggable` включает штатный drag React Flow и блокирует pan над ней. Неактивные клеточки остаются доступны для pan; `onNodeClick` активирует их только при клике. Штатный обработчик pan подавляет click после перемещения мыши, поэтому отпускание неактивной клеточки не меняет выделение. Корень и единственный ребёнок не переставляются независимо от активности.

Штатные shortcuts React Flow для перемещения геометрии отключены. Собственный keyboard layer выполняет доменные операции; редактор строки использует локальный draft. Awareness не является надёжным lock: concurrent offline commits разрешаются заменой одной целой строки.

Undo/redo реализуется `Y.UndoManager` для `nodes`, `orders`, `deletions` и `settings`, с отслеживанием только origins команд этой вкладки и `captureTimeout: 0`. Инициализация записей узлов не входит в историю, их видимость управляется маркером создания. Независимые маркеры удаления не позволяют undo одного участника отменить concurrent delete другого. Отмена первого изменения настройки может удалить её ключ, возвращая значение по умолчанию; обязательные поля узла защищены от удаления. История существует только в памяти; редактор draft использует нативный undo браузера, в том числе для `Shift+Enter`. Подробности — в xref:tree-semantics.adoc[`tree-semantics.adoc`].

Схема 2 добавляет `deletions`; при загрузке сервер обновляет метаданные схемы 1, сохраняя прежние tombstones. Имя IndexedDB-кеша остаётся прежним; готовность клиента определяется `schemaVersion`, а не именем кеша. После обновления сервера клиентам требуется перезагрузка и синхронизация; неизвестные версии схемы отклоняются.

Важно различать:

* перестановку sibling-узлов как доменную операцию;
* свободное перетаскивание узла как UI-жест, который приводит к изменению порядка или parent relationship.

Не следует хранить обычный drag как произвольные координаты, если его смысл можно выразить структурной операцией.

== 9. Collaboration и модель дерева

Наивная модель вида:

[listing]
----
Node {
  children: [...]
}
----

может создать проблемы при concurrent reparent.

У узла единственный parent relationship:

[listing]
----
Node {
  id
  placement: { parentId, placementId }
}
----

Для MVP принята модель из xref:tree-semantics.adoc[`tree-semantics.adoc`]: узел содержит одно атомарное значение `placement`, а отдельные `Y.Array` содержат placement-записи для порядка детей. Неактивные записи фильтруются по текущему placement узла.

Raw Yjs state может содержать конфликтные placements. Чистая детерминированная проекция устраняет orphan relationships и циклы, не порождая repair updates.

== 10. Текст узла

Rich-text editor в первой версии не нужен.

Предпочтительно:

* plain text;
* атомарный commit всей строки без collaborative character-level merge;
* automatic wrapping;
* automatic height;
* динамическое измерение node size;
* relayout после изменения размера.

В MVP используется фиксированная ширина 280 px и автоматическая высота.

== 11. Backend scope

Backend должен оставаться небольшим.

Обязанности MVP:

* выдача static frontend;
* WebSocket collaboration;
* persistence;
* backup-friendly storage.

Не следует вводить отдельные сервисы, пока нет реальной необходимости.

== 12. Auth

В MVP auth выключен, приложение рассчитано на trusted network. Дальнейшее решение не принято.

Желательный диапазон вариантов:

[listing]
----
AUTH_MODE=none
AUTH_MODE=password
AUTH_MODE=oidc
----

Но это пока не обязательный контракт.

Для закрытой среды допускается максимально простой режим.

== 13. Что пока сознательно не проектируем

* горизонтальное масштабирование;
* Redis;
* Kubernetes;
* сложный multi-tenancy;
* billing;
* публичный SaaS;
* сложный RBAC;
* аналитическое хранилище;
* distributed transactions;
* отдельный Spring Boot backend.

Если что-то из этого когда-нибудь понадобится, решение должно приниматься по фактической потребности.
