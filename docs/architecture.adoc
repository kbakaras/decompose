= Decompose: архитектура
:figure-caption: Рисунок

== 1. Архитектурные цели

Архитектура должна соответствовать реальному масштабу проекта:

* небольшая команда разработчиков;
* максимум одна компания;
* self-hosted использование;
* один экземпляр приложения в обычном сценарии;
* отсутствие требований Internet-scale SaaS.

Основной принцип:

[quote]
____
Использовать готовые компоненты для rendering, layout и collaboration; собственный код сосредоточить на предметной модели и UX Decompose.
____

== 2. Текущий выбранный стек

=== Frontend

* TypeScript
* React
* React Flow — canvas, nodes, edges, viewport, selection и drag для sibling reorder; свободное размещение выключено
* ELK.js — автоматический hierarchical layout
* Yjs — CRDT и collaborative data model
* y-indexeddb — локальное хранение Yjs-документа в браузере

=== Backend

* Node.js 24 LTS
* TypeScript
* Hocuspocus — WebSocket collaboration server для Yjs, встроенный в основной backend
* SQLite — бинарное состояние Yjs через `@hocuspocus/extension-sqlite`

=== Тесты

Используются:

* Vitest — unit tests
* fast-check — property-based tests для операций над деревом и инвариантов
* Playwright — UI и multi-client collaboration tests

== 3. Целевая схема

[listing]
----
┌─────────────────────────────────────────────┐
│ Browser                                     │
│                                             │
│ React                                       │
│ React Flow                                  │
│ ELK.js                                      │
│ Yjs                                        │
│ y-indexeddb                                │
└──────────────────┬──────────────────────────┘
                   │
                HTTP / WS
                   │
┌──────────────────▼──────────────────────────┐
│ Decompose backend                           │
│                                             │
│ Node.js + TypeScript                        │
│ HTTP API                                    │
│ Hocuspocus                                  │
│ Auth: none (MVP)                             │
└──────────────────┬──────────────────────────┘
                   │
┌──────────────────▼──────────────────────────┐
│ SQLite                                      │
└─────────────────────────────────────────────┘
----

Ожидаемый deployment:

[listing]
----
docker compose
└── decompose
    └── persistent volume
        └── decompose.sqlite
----

Цель: один application service и один persistent volume.

Реализация использует HTTP-сервер Hocuspocus и Express для static frontend и `/healthz` на том же порту. WebSocket доступен только на `/collaboration`, принимается только документ `main`. Используется штатный lifecycle Hocuspocus для закрытия соединений и сохранения перед остановкой.

Первый root создаётся сервером; клиенты не инициализируют конкурирующие документы. IndexedDB загружается до подключения provider. Production service worker кеширует оболочку приложения для offline reload; в dev-сборке он выключен.

== 4. Почему Node.js

Node.js выбран не как универсально «лучший backend», а как самый прямой путь к зрелому Yjs/Hocuspocus стеку.

Преимущества для MVP:

* Hocuspocus работает в родной экосистеме;
* frontend и backend используют TypeScript;
* можно разделять общие типы;
* меньше собственной реализации collaboration protocol;
* ниже риск ошибок в CRDT sync.

Go + ygo остаётся потенциальной альтернативой на будущее, если появится реальная польза от single binary и более лёгкого runtime. Для MVP переход на Go не планируется.

== 5. Почему SQLite

SQLite выбран как основное хранилище, потому что ожидаемый масштаб невелик:

* один backend instance;
* небольшое число пользователей;
* умеренное число документов;
* отсутствие тяжёлой серверной аналитики;
* отсутствие сложного multi-tenant SaaS.

PostgreSQL не требуется на старте.

Переход к PostgreSQL следует рассматривать только при появлении конкретной причины, а не заранее.

== 6. Разделение состояния

Состояние нужно разделять как минимум на три категории.

=== 6.1. Domain state

Хранится и синхронизируется через Yjs.

Примеры:

* node id;
* text;
* status;
* parent;
* sibling order;

Типы узлов (`kind`) и другие семантические свойства в MVP не входят.

Текст клеточки хранится как атомарная строка, а не как `Y.Text`. Во время ввода используется локальный draft; в Yjs записывается результат целиком.

=== 6.2. Presence

Эфемерное состояние collaboration.

Примеры:

* пользователь online;
* выбранный узел;
* редактируемый узел;
* cursor/presence metadata.

Используется Yjs Awareness.

=== 6.3. Local UI state

Не синхронизируется как доменная модель.

Примеры:

* viewport;
* zoom;
* локальное выделение;
* открытое меню;
* промежуточная геометрия layout.

Используется React state.

== 7. Structure is data; coordinates are view

Предварительное решение:

Не хранить вычисленные `x/y` как источник истины.

В предметной модели хранить:

* parent relationship;
* sibling order;
* возможно, explicit layout hints, если они реально понадобятся.

ELK.js вычисляет координаты на клиенте.

Это означает, что два клиента могут иметь немного различную пиксельную геометрию при сохранении одной и той же смысловой структуры.

== 8. Layout

Основной алгоритм:

* ELK layered;
* направление слева направо;
* layout должен уважать model order;
* по возможности учитывать mental map пользователя при перестроении.

Включены `considerModelOrder.strategy=NODES_AND_EDGES` и `crossingMinimization.forceNodeModelOrder=true`. Входные nodes/edges строятся в порядке обхода проекции. ResizeObserver измеряет высоту клеточек; размеры и координаты остаются локальными. React Flow получает измеренные размеры при каждом обновлении controlled nodes.

Новая клеточка монтируется прозрачно для измерения и приёма ввода, но показывается вместе со связью только после layout с измеренными размерами. Промежуточная позиция `(0, 0)` не видна. Drag использует штатные callbacks React Flow и локальную preview-позицию; во время жеста ELK не перестраивает схему. После drop preview сохраняется до готовности нового layout, без возврата на старое место между кадрами.

При первом открытии и reload вся диаграмма скрыта до измерения узлов, готовности ELK и установки начального viewport без анимации. Bounds вычисляются из результата layout; `getViewportForBounds` и `setViewport` React Flow вписывают схему до её показа. Отложенный по таймеру `fitView` не используется. Автопрокрутка к active node включается только при последующем изменении цели, чтобы не конкурировать с начальным вписыванием.

Штатные shortcuts React Flow для перемещения геометрии отключены. Собственный keyboard layer выполняет доменные операции; редактор строки использует локальный draft. Awareness не является надёжным lock: concurrent offline commits разрешаются заменой одной целой строки.

Undo/redo реализуется `Y.UndoManager` для `nodes`, `orders` и `deletions`, с отслеживанием только origins доменных команд этой вкладки и `captureTimeout: 0`. Инициализация записей узлов не входит в историю, их видимость управляется маркером создания. Независимые маркеры удаления не позволяют undo одного участника отменить concurrent delete другого. История существует только в памяти; редактор draft использует нативный undo браузера. Подробности — в xref:tree-semantics.adoc[`tree-semantics.adoc`].

Схема 2 добавляет `deletions`; при загрузке сервер обновляет метаданные схемы 1, сохраняя прежние tombstones. Имя IndexedDB-кеша остаётся прежним; готовность клиента определяется `schemaVersion`, а не именем кеша. После обновления сервера клиентам требуется перезагрузка и синхронизация; неизвестные версии схемы отклоняются.

Важно различать:

* перестановку sibling-узлов как доменную операцию;
* свободное перетаскивание узла как UI-жест, который приводит к изменению порядка или parent relationship.

Не следует хранить обычный drag как произвольные координаты, если его смысл можно выразить структурной операцией.

== 9. Collaboration и модель дерева

Наивная модель вида:

[listing]
----
Node {
  children: [...]
}
----

может создать проблемы при concurrent reparent.

У узла единственный parent relationship:

[listing]
----
Node {
  id
  placement: { parentId, placementId }
}
----

Для MVP принята модель из xref:tree-semantics.adoc[`tree-semantics.adoc`]: узел содержит одно атомарное значение `placement`, а отдельные `Y.Array` содержат placement-записи для порядка детей. Неактивные записи фильтруются по текущему placement узла.

Raw Yjs state может содержать конфликтные placements. Чистая детерминированная проекция устраняет orphan relationships и циклы, не порождая repair updates.

== 10. Текст узла

Rich-text editor в первой версии не нужен.

Предпочтительно:

* plain text;
* атомарный commit всей строки без collaborative character-level merge;
* automatic wrapping;
* automatic height;
* динамическое измерение node size;
* relayout после изменения размера.

В MVP используется фиксированная ширина 280 px и автоматическая высота.

== 11. Backend scope

Backend должен оставаться небольшим.

Обязанности MVP:

* выдача static frontend;
* WebSocket collaboration;
* persistence;
* backup-friendly storage.

Не следует вводить отдельные сервисы, пока нет реальной необходимости.

== 12. Auth

В MVP auth выключен, приложение рассчитано на trusted network. Дальнейшее решение не принято.

Желательный диапазон вариантов:

[listing]
----
AUTH_MODE=none
AUTH_MODE=password
AUTH_MODE=oidc
----

Но это пока не обязательный контракт.

Для закрытой среды допускается максимально простой режим.

== 13. Что пока сознательно не проектируем

* горизонтальное масштабирование;
* Redis;
* Kubernetes;
* сложный multi-tenancy;
* billing;
* публичный SaaS;
* сложный RBAC;
* аналитическое хранилище;
* distributed transactions;
* отдельный Spring Boot backend.

Если что-то из этого когда-нибудь понадобится, решение должно приниматься по фактической потребности.
