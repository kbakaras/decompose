= Decompose: описание продукта
:figure-caption: Рисунок

== 1. Назначение

Decompose — специализированный collaborative-инструмент для декомпозиции больших задач, вопросов, проблем и рассуждений на иерархию более мелких смысловых единиц.

Основной сценарий использования:

. Пользователь создаёт корневой узел, представляющий задачу или предмет размышления целиком.
. Разбивает его на дочерние узлы.
. Продолжает декомпозицию на несколько уровней.
. Меняет порядок элементов по мере осмысления задачи.
. Отмечает состояние отдельных узлов.
. Работает преимущественно с клавиатуры.
. При необходимости делает это одновременно с другими участниками команды.

Инструмент рассчитан прежде всего на небольшую команду разработчиков, максимум — на использование внутри одной компании.

== 2. Почему не обычный mindmap

Decompose визуально может напоминать mindmap, но модель продукта должна быть другой.

Обычный mindmap в первую очередь представляет набор графических узлов и связей. В Decompose узел — это смысловая единица предметной модели.

Прямоугольник на экране — лишь визуальное представление узла.

Например:

* цвет не должен быть единственным носителем статуса;
* положение по вертикали не должно быть единственным носителем порядка;
* связь parent/child должна храниться в модели;
* sibling order должен храниться в модели;
* координаты должны вычисляться layout engine.

== 3. Product philosophy

=== 3.1. Diagram is not the data model

Диаграмма является представлением структуры, а не самой структурой.

=== 3.2. Nodes have meaning

Узел представляет смысловую единицу: задачу, вопрос, решение, проблему, гипотезу, заметку, группу или иной тип, если он будет явно введён в модель.

Не следует заранее считать каждый узел `Task`.

В MVP узел, или клеточка, является минимальной единицей совместного редактирования. Его текст заменяется целиком: совместное посимвольное редактирование одной клеточки не требуется.

=== 3.3. Appearance follows semantics

Цвет, рамка, иконка и прочие визуальные признаки должны по возможности вытекать из семантики узла.

Например:

[listing]
----
status = open  -> yellow
status = done  -> green
----

Но конкретная тема отображения не должна менять смысл данных.

=== 3.4. Structure is first-class data

Parent/child relationship и порядок sibling-узлов являются частью данных.

Layout не должен самопроизвольно менять смысловой порядок детей только ради более красивой картинки.

=== 3.5. Layout is a view

Геометрия вычисляется автоматически.

Пользователь управляет прежде всего:

* структурой;
* порядком;
* семантикой;
* возможно, отдельными layout hints.

Точные координаты узлов не должны быть основной частью предметной модели.

=== 3.6. Keyboard-first

Основные операции должны соответствовать смысловым действиям пользователя:

* создать child;
* создать sibling;
* перейти к parent;
* перейти к child;
* изменить sibling order;
* indent;
* outdent;
* изменить статус;
* начать редактирование текста.

Пользователь не должен ощущать, что он вручную рисует прямоугольники и стрелки.

=== 3.7. Узкая специализация

Decompose не должен превращаться в:

* Miro;
* Jira;
* универсальный diagram editor;
* полноценный project management suite;
* календарь;
* Gantt;
* Scrum board;
* time tracker.

Если позже понадобится связь с внешними системами, предпочтительнее интеграция или ссылка на внешний объект, а не дублирование всей чужой функциональности.

=== 3.8. Простота эксплуатации

Проект должен быть пригоден для self-hosted использования небольшой командой.

Приоритет:

* один application service;
* один persistent volume;
* минимальное количество внешней инфраструктуры;
* простой backup;
* простой upgrade.

== 4. Исходные функциональные требования

=== 4.1. Collaboration

* Одновременное редактирование документа несколькими пользователями.
* Участники могут одновременно работать с разными клеточками; текст одной клеточки не объединяется посимвольно.
* Изменения должны сходиться детерминированно.
* Пользователь должен видеть присутствие других участников.
* Желательно отображать, какой узел редактирует другой пользователь.
* В MVP offline-редактирование уже загруженного документа обязательно; новое первое открытие требует сервера.

=== 4.2. Иерархическое представление

* Основной layout — слева направо.
* Узлы одного уровня располагаются по вертикали.
* Пользователь должен явно влиять на порядок sibling-узлов.
* Порядок детей одного parent можно менять клавиатурой или перетаскиванием за любую часть клеточки вне редактирования текста. Drag не меняет parent.
* Layout engine должен уважать этот порядок.
* Желательно сохранить ощущение стабильности схемы при небольших изменениях, чтобы пользователь не терял mental map.

=== 4.3. Текст в узлах

* Текст переносится автоматически.
* Высота узла подстраивается под содержимое.
* В MVP ширина фиксирована: 280 px; высота автоматическая.
* Rich-text в первой версии не требуется.
* Внутри клеточки отображается только её текст, без номера, подписей статуса, участников и служебных сообщений. Статус и presence остаются в модели, доступны в подсказке и для screen reader; текст `done` не зачёркивается. Отступы компактные, фон `open` — жёлто-оранжевый, `done` — зелёный.
* Рамка и тень выделения, в том числе при редактировании, соответствуют цвету статуса клеточки.
* Указатель различает действия мышью: открытая ладонь для перемещения холста, сжатая — во время этого жеста; стрелки перемещения для перестановки клеточки; текстовый указатель внутри редактора. Корень и клеточки без возможности перестановки перемещают холст и используют ту же ладонь, что и пустое место.
* Undo/redo отменяет и повторяет собственные действия текущей вкладки: сохранение текста, статус, создание, перемещение и удаление. История не сохраняется после перезагрузки. В редакторе отмена относится к несохранённому тексту; подробная concurrent-семантика описана в xref:tree-semantics.adoc[`tree-semantics.adoc`].
* `Enter` в редакторе сохраняет текст и возвращает навигацию, не создавая узел. Новый sibling создаётся отдельным нажатием `Enter` в режиме навигации.

=== 4.4. Состояние узлов

Минимально нужен явный статус, как минимум эквивалентный:

* open;
* done.

Вероятные дополнительные состояния:

* in-progress;
* blocked;
* irrelevant/cancelled.

Точный набор пока не определён.

=== 4.5. Типы узлов

Вероятные типы:

* task;
* question;
* decision;
* problem;
* hypothesis;
* note;
* group.

Точный набор и необходимость типов вообще ещё требуют отдельного решения.

== 5. UX-ориентиры

Холст занимает всю область окна под одной компактной верхней панелью. В ней находятся название документа, соединение и presence, undo/redo, вписывание схемы, справка и меню редких действий с клеточкой. Отдельных полос заголовка, инструментов, слоганов и нижнего status bar нет. Ошибки и предупреждения о занятом редакторе показываются компактным закрываемым уведомлением поверх холста; обычные подсказки не занимают его площадь.

Исторически исходный workflow строился вокруг yEd:

* прямоугольники;
* связи;
* иерархия слева направо;
* быстрый автоматический layout;
* возможность влиять на вертикальный порядок;
* хорошая работа с клавиатурой;
* минимальный интерфейсный барьер после привыкания.

Decompose должен сохранить эту скорость, но заменить неявные визуальные договорённости явной семантической моделью и добавить collaboration.

== 6. Рабочее название

Текущее имя проекта: Decompose.

Оно хорошо отражает назначение, но уже используется рядом существующих проектов.

Hiro нужно сохранить в документации как возможный вариант будущего переименования, если проект выйдет за рамки внутреннего использования или потребуется более уникальное публичное имя.
