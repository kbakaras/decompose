# Decompose: открытые вопросы

Этот файл содержит вопросы, которые ещё не решены.

Codex не должен молча превращать их в архитектурные факты. Если для реализации нужен ответ, следует либо выбрать минимальное обратимое решение и явно его зафиксировать, либо остановиться на уровне проектирования.

## 1. Предметная модель узла

Нужно определить минимальный набор полей узла.

Предварительные кандидаты:

```text
id
text
kind
status
parentId
orderKey
```

Вопросы:

- Нужен ли `kind` в первой версии?
- Какие `kind` действительно полезны?
- Какие `status` нужны кроме `open/done`?
- Должен ли статус родителя вычисляться из детей?
- Можно ли иметь узел без parent?
- Сколько root nodes допустимо?

## 2. Иерархия

Нужно определить инварианты дерева.

Предварительно ожидается:

- один root;
- у каждого не-root узла ровно один parent;
- циклы запрещены;
- sibling order детерминирован;
- после merge документ должен оставаться валидным.

Нужно проверить, достижимы ли эти инварианты естественно поверх Yjs.

## 3. Concurrent operations

Нужно отдельно спроектировать semantics для случаев:

- A перемещает X под P1, B одновременно под P2;
- A удаляет X, B редактирует текст X;
- A удаляет subtree, B перемещает узел из этого subtree;
- два клиента одновременно меняют sibling order;
- два клиента одновременно создают sibling в одной позиции;
- операция создаёт цикл на одном клиенте относительно конкурентных изменений другого.

## 4. Sibling ordering

Нужно выбрать представление порядка.

Возможные варианты:

- Y.Array детей;
- `orderKey`;
- fractional indexing;
- иная CRDT-friendly схема.

Критерии:

- устойчивость при concurrent inserts/moves;
- минимум массовых перенумераций;
- простота алгоритма;
- deterministic convergence.

## 5. Layout hints

Нужно решить, достаточно ли semantic order, или необходимо хранить дополнительные пользовательские подсказки layout engine.

Например:

- preferred relative position;
- preferred side;
- local ordering constraints.

По умолчанию предпочтительнее не хранить координаты.

## 6. Размер узла

Нужно определить UX:

- фиксированная ширина + auto height;
- ширина в диапазоне min/max;
- автоматическая ширина;
- ручное изменение ширины;
- синхронизируется ли ширина как часть документа.

Требование: длинный текст должен читаться без ручной подгонки высоты.

## 7. Keyboard model

Нужно формализовать основной набор клавиш.

Предварительная идея:

```text
Enter        create sibling
Tab          create child / indent
Shift+Tab    outdent
F2           edit
Space        toggle status
Ctrl+Up      move sibling up
Ctrl+Down    move sibling down
Left/Right   parent/child navigation
Up/Down      sibling navigation
```

Это только гипотеза, не зафиксированный контракт.

Нужно проверить конфликт с редактированием текста и browser shortcuts.

## 8. Drag-and-drop

Нужно определить точный смысл drag:

- только reorder siblings;
- reparent;
- оба варианта;
- возможность временно менять визуальное положение без структурного изменения.

Предпочтение: drag должен завершаться доменной операцией, а не сохранением произвольных координат.

## 9. Collapse/expand

Нужно решить:

- является ли collapsed state частью документа;
- или это локальное представление каждого пользователя.

Вероятно, локальное состояние удобнее, но возможны сценарии совместного представления.

## 10. Completion semantics

Нужно решить:

- является ли `done` только ручным статусом;
- может ли parent автоматически становиться `done`, если все дети done;
- что происходит при добавлении нового open child к done parent;
- должен ли progress рассчитываться автоматически.

## 11. Auth и permissions

Для внутреннего использования нужно определить минимально достаточный вариант.

Возможные режимы:

- без auth в trusted network;
- встроенный login/password;
- OIDC.

Также нужно решить, достаточно ли:

- все пользователи видят все документы;
- owner/editor/viewer;
- более сложные правила не требуются.

## 12. Документ и workspace

Нужно определить, существует ли сущность workspace/project, или достаточно списка документов.

Не следует вводить workspace без реального сценария.

## 13. Поиск и навигация

Пока не определено:

- full-text search;
- поиск только внутри текущего документа;
- глобальный search;
- jump-to-node;
- backlinks.

Нужно добавлять только после появления конкретных сценариев.

## 14. Импорт/экспорт

Пока не определено.

Возможные направления:

- JSON;
- Markdown outline;
- SVG/PNG;
- PDF;
- yEd GraphML.

Ни одно из них не является обязательным для первого MVP.

## 15. Название

Рабочее имя: `Decompose`.

Возможный вариант будущего переименования: `Hiro`.

Переименование имеет смысл рассматривать только при необходимости публичного бренда.
