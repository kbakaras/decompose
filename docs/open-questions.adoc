= Decompose: открытые вопросы
:figure-caption: Рисунок

Этот файл содержит вопросы, которые ещё не решены. Зафиксированная модель MVP описана в xref:tree-semantics.adoc[`tree-semantics.adoc`].

Codex не должен молча превращать перечисленные варианты в архитектурные факты. Если для реализации нужен ответ, следует выбрать минимальное обратимое решение и явно его зафиксировать либо остановиться на уровне проектирования.

== 1. Layout hints и mental map

Для уменьшения скачков при перестановке соседей выбран режим ELK `BALANCED`, без привязки к предыдущим координатам. Нужно проверить на других схемах, достаточно ли этого режима и semantic sibling order для ощущения стабильности после небольших изменений.

Дополнительные layout hints и координаты не следует добавлять до появления воспроизводимого проблемного сценария.

== 2. Collapse/expand

Collapse/expand не входит в MVP. Если функция понадобится, нужно отдельно решить, является ли collapsed state локальным представлением или частью совместного документа.

== 3. Completion semantics

В MVP `open/done` — только ручной статус. Открыты вопросы:

* должен ли parent автоматически зависеть от статусов детей;
* что происходит при добавлении `open` child к `done` parent;
* нужен ли вычисляемый progress.

== 4. Auth и permissions

MVP работает без auth в trusted network. Для следующего этапа возможны встроенный login/password или OIDC. Тогда же нужно решить, нужны ли роли owner/editor/viewer.

== 5. Документы и workspace

Обычные схемы и деревья задач трекера разделены в каталоге. Задача открывается по постоянному ключу `/tracker/{key}` без интеграции с API трекера. Каждая схема — независимый документ Yjs, название определяется текстом корня. Корень приложения показывает титульную страницу без документа; основной схемы нет, прежний `main` удаляется без переноса в обычную схему. Удаление обычных схем и задач выполняется после подтверждения без корзины; повторное создание удалённой задачи — явное действие с новым ID. Привязка ранее созданных схем к задачам и отдельная сущность workspace/project остаются открытыми вопросами.

== 6. Поиск и навигация

Для задач трекера поддерживается поиск подстроки по ключу и тексту корня, для обычных схем — по названию в каталоге. Карточка дерева задачи может содержать одну направленную ссылку на ключ другой задачи. Обратный индекс и backlinks не строятся. Поиск по содержимому дочерних карточек, global search, jump-to-node, проверка битых ссылок и восстановление выбранной карточки после возврата по истории не определены. Их следует добавлять только под конкретные сценарии.

== 7. Импорт и экспорт

Поддерживается импорт направленного дерева из yEd GraphML и собственный формат `.deco` для сохранения, восстановления и редактирования файла на диске; границы описаны в xref:product.adoc[описании продукта]. Экспорт GraphML, Markdown outline, SVG/PNG и PDF не реализован. Передача роли владельца файла другому участнику и объединение внешних изменений файла не предусмотрены; их необходимость остаётся открытой.

== 8. Undo и удаление данных

В MVP есть локальная undo/redo-история текущей вкладки; concurrent-семантика зафиксирована в xref:tree-semantics.adoc[`tree-semantics.adoc`]. История не переживает перезагрузку. Срок хранения скрытых узлов и маркеров, физическая очистка и необходимость долговременной истории остаются открытыми; автоматическая очистка пока не выполняется.

== 9. Offline-создание документа

Уже загруженный документ можно редактировать offline. Создание совершенно нового документа без первого соединения с backend пока не поддерживается.

== 10. Название

Русскоязычное название — дерево·дел; английское название проекта decompose сохраняется. Правила написания зафиксированы в xref:product.adoc[описании продукта].

== 11. Расширение минимальной модели

В MVP нет `kind`, а статусы ограничены `open/done`. Нужны ли типы клеточек или дополнительные ручные статусы, решаем по опыту использования прототипа; перечисленные в xref:product.adoc[`product.adoc`] варианты не являются обязательствами реализации.
